 3. RUNNING THE MODEL
================================================================================

Always activate the env first:

    source /home/raiyan/anaconda3/etc/profile.d/conda.sh
    conda activate memedecoder
    cd /home/raiyan/PR/memedecoder_2/Scripts

--------------------------------------------------------------------------------
 3a. Smoke test - 2 minutes, run this before any long run
--------------------------------------------------------------------------------

    python main.py --subset 24 --n_iter 1 --run_name smoketest

This exercises the entire path: load -> train -> validate -> checkpoint -> reload
-> test -> metrics -> write Outputs/. It should finish at about 20.8% accuracy.

THAT NUMBER IS NOT A RESULT. It is 24 training memes for one epoch against a 25%
four-class chance baseline. It proves the plumbing works and nothing else.

First ever run also downloads Bangla-BERT (~650 MB) and CLIP ViT-B/32 (~350 MB)
into .cache/, so allow extra time and network for that one.

--------------------------------------------------------------------------------
 3b. The real run - about 21 minutes on the 5060 Ti
--------------------------------------------------------------------------------

    python main.py --run_name maf_full

Defaults are the paper's Appendix A setup: batch 4, 20 epochs, lr 5e-5, 16 heads,
max_len 70, seed 42. You do not need to pass any of them.

Ignore README.md section 5.7, which says this machine has no CUDA GPU and that
full training is a multi-day job best sent to Colab or Kaggle. That was true of
the original Windows machine. Here it is a 21-minute local run.

To run it detached so it survives the terminal closing:

    nohup python main.py --run_name maf_full > /dev/null 2>&1 &

The console log still lands in Logs/ either way (see section 4), so sending stdout
to /dev/null loses nothing.

================================================================================
 4. CONSOLE LOGS  (added 2026-09-19)
================================================================================

Every main.py run now tees its complete console output to:

    /home/raiyan/PR/memedecoder_2/Logs/<run_name>_<timestamp>.log

This exists because the per-epoch training curve was previously printed to the
terminal and nowhere else. results_<run>.json keeps the final test metrics but not
the epoch-by-epoch validation accuracy, so closing the terminal destroyed the only
evidence of whether a run over-fitted and at which epoch the checkpoint was taken.

The terminal behaves exactly as before - tqdm still draws live progress bars. In
the file, each progress bar is collapsed to a single line showing its final state,
so a 20-epoch run produces a readable log rather than tens of thousands of partial
redraws. Each log carries a header (timestamp, exact command, cwd, Python version)
and a footer with the finish time.

To disable for a given run:

    python main.py --run_name whatever --no_log

Logs are never cleaned up automatically. They are a few KB each. Delete them with:

    rm /home/raiyan/PR/memedecoder_2/Logs/*.log

Implementation is Scripts/_logging.py. To add the same capture to another script,
the whole change is two lines after its arguments are parsed:

    import _logging
    _logging.start("some_name")

    Accuracy      0.460
    Weighted F1   0.451
    Macro F1      0.448
    MMAE          0.917
    Best val acc  0.733  (reached at epoch 9 of 20)
    Wall time     1253s

Per class, F1: RAg 0.615, PAg 0.424, NoAg 0.387, GAg 0.366.

Two things to understand before you compare any future run to this:

1. The gap between 73.3% validation and 46.0% test is expected, and is a property
   of the dataset rather than a bug. README.md section 6 documents that the train
   and test splits have different class priors: NoAg is 33.1% of train but only
   18.8% of test, while PAg is 20.8% of train and 32.0% of test. The confusion
   matrix shows the consequence directly - 50 of the 128 true PAg memes are
   predicted NoAg. A model that correctly learns the training prior is miscalibrated
   for this test set. Macro F1 is the more trustworthy metric here.

2. This is far below the paper's published WF1 = 0.742, as README.md section 5
   predicts it should be. Our captions are raw machine OCR; the paper's were
   hand-corrected. Also this task is 4-way where the paper's was 5-way. The two
   effects push in opposite directions and do not cancel in any principled way, so
   this number replicates the METHOD, not the published SCORE.

================================================================================
 7. THE VLM APPROACH  (added 2026-09-19)
================================================================================

A second, quite different attack on the same problem: instead of OCR-ing the meme and
feeding the text to Bangla-BERT, hand the meme image straight to a vision-language
model and ask it which class the meme belongs to.

WHY IT WORKS SO MUCH BETTER

README.md section 5.1 names caption noise as the largest single source of divergence
from the published result. MAF never sees the meme's text - it sees whatever
pytesseract managed to extract, and Bengali OCR is weak enough that the paper's own
authors hand-corrected every caption by hand. A VLM reads the image directly, so the
OCR stage and all of its errors leave the pipeline entirely.

Scripts/vlm_probe.py shows that gap directly. On testimage013.jpg:

    Tesseract : সস্্ৃস্স্স Rl ani চে AK] যা TEJGAON ... রা / w= Kanyan Bazar 00 2 an,
    Qwen3-VL  : তেজগাও / আবুল হোটেল / রমনা পার্ক / ঢাকা নিউ মার্কেট / Karwan Bazar

Same image. One is noise, the other is the actual text. That is the whole argument.

HOW A PREDICTION IS MADE

The four classes are offered as lettered options A-D and the class is read off by
comparing the logits of exactly those four tokens at the first answer position. This
always returns a valid class (no unparseable free-text answers silently scored as
wrong), it is one forward pass rather than an autoregressive decode, and it is
deterministic - a rerun reproduces the number exactly. Pass --decode text to generate
free text and parse it instead; that mode counts and reports unparsed answers.

--------------------------------------------------------------------------------
 7a. Check the model can read Bengali  (~2 min, do this first on a new machine)
--------------------------------------------------------------------------------

    cd /home/raiyan/PR/memedecoder_2/Scripts
    python vlm_probe.py --n 4

Prints, per meme, the Tesseract caption next to the VLM's transcription. Judge by eye.
If the VLM cannot read the Bengali, everything below is measuring the wrong thing and

Variants:

--------------------------------------------------------------------------------
 7c. QLoRA fine-tune  (~3.5 h for 2 epochs on the 5060 Ti)
--------------------------------------------------------------------------------

    python vlm_finetune.py --subset 32 --epochs 1 --run_name vlm_ft_smoke  # ~3 min
    python vlm_finetune.py --run_name vlm_finetuned --epochs 2             # the real run

RUN THE SMOKE TEST FIRST. It costs three minutes and exercises the whole path. Two
real bugs were caught this way rather than three hours into a full run.

The base weights stay frozen in 4-bit and only LoRA adapters train, which is what
keeps an 8B model inside 16 GB alongside the vision tower. Loss is computed on the
single answer token - every prompt token is masked to -100 - so training optimises
exactly the position inference reads, with no train/test mismatch.

The adapter is saved to Saved_Models/lora_<run_name>/ and is a few MB, not the ~1 GB
a MAF checkpoint costs.

EXPECT THIS TO POSSIBLY SCORE BELOW ZERO-SHOT. Fine-tuning teaches the training
distribution (NoAg 33.1%), and the test set has NoAg at 18.8% and PAg at 32.0%. That
is the same prior mismatch that sank MAF, described in README.md section 6. Zero-shot
carries no such bias because it never saw the training prior at all. If the fine-tuned
number lands lower, that is a finding about the dataset, not a broken run.

--------------------------------------------------------------------------------
 7d. Known gotchas in this code
--------------------------------------------------------------------------------

Qwen3-VL returns several parallel per-token tensors (input_ids, attention_mask,
mm_token_type_ids) and computes its 3D rope index from them jointly. Appending an
answer token to some but not all of them raises a shape mismatch deep inside the
model. vlm_finetune.py therefore appends the answer as a chat MESSAGE and lets the
processor build the whole sequence. Do not "optimise" that back into tensor surgery.

The letters A-D appear in the prompt as well as in the answer, so the answer token is
located by its LAST occurrence in the sequence, not its first.

--------------------------------------------------------------------------------
 7f. WHY FINE-TUNING SCORED WORSE THAN ZERO-SHOT
--------------------------------------------------------------------------------

The headline pair looks like a failed fine-tune:

    test set (400 memes)      zero-shot 0.720    fine-tuned 0.680

It is not. Running the untrained model on the VALIDATION split as a control shows what
actually happened:

                              zero-shot   fine-tuned   change
    validation (513 memes)      0.626       0.803      +17.7 points
    test       (400 memes)      0.720       0.680       -4.0 points

Fine-tuning worked, and worked well - it added nearly 18 points on the distribution it
was trained on. The gain simply does not survive the move to the test set, because the
two splits do not have the same class priors. From README.md section 6:

                       train/validation      test
    NoAg                    33.1%           18.8%
    PAg                     20.8%           32.0%

Fine-tuning taught the model the training prior, so it predicts NoAg far more often:

                       times NoAg predicted    NoAg precision   (75 are truly NoAg)
    zero-shot                   65                 0.600
    fine-tuned                 103                 0.495

That is the same failure that sank MAF, which sent 50 of 128 political memes to NoAg.
The zero-shot model is immune to it for the simple reason that it never saw the
training prior at all.

Note also that zero-shot scores HIGHER on test (0.720) than on validation (0.626).
The splits are not equally hard: NoAg is the zero-shot model's weakest class, and the
test set contains proportionally far fewer NoAg memes. Never compare a validation
number here against a test number and read the difference as progress.

If you want the fine-tuned model to transfer, the fix is prior correction, not more
epochs - e.g. class-weighted loss, resampling the training split toward the test
prior, or adjusting the decision threshold on the four logits at inference time.
